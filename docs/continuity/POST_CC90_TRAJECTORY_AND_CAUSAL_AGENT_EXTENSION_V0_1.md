# After CC-90-001: five primitives for persistent trajectory

## Proposed model

Identity + history + trajectory is a helpful position/velocity analogy for autonomous characters. It does not make an LLM act when a computer is off. A real scheduler and policy/execution loop are separately required.

1. ANCHOR: read-only to runtime agents; versioned Creator-correctable via append-only supersession and source receipt. Text claiming to be Noah.Physical is not credential proof.
2. RELATIONSHIP STATE: relational observations, permissions, commitments and unresolved tensions, each evidence-backed. Never insert an arbitrary trust value like 0.85 as measured fact.
3. COMMITMENT LIFECYCLE: PROPOSED -> ACCEPTED -> ACTIVE -> SATISFIED or BROKEN or ABANDONED; any transition must be linked to actual events and state policy.
4. CONSEQUENCE GRAPH: typed directed cause and effect edges with a receipt for each source and a separate uncertainty status. No unsupported causal smoothing.
5. TRAJECTORY ENGINE: grounded goal *candidates* from independent repeated observations, with counterevidence and review. Candidate does not mean action permission.

## Implementation sketch for a future authorized coding agent

~~~text
on_tick(world_branch, clock, principal):
    require scheduler_running == true
    state = load_events_and_replay(world_branch)
    due = list_due_accepted_commitments(state, clock)
    candidate = propose_action_from(state, due, permitted_knowledge)
    require capability_policy_allows(principal, candidate)
    require world_preconditions_hold(candidate)
    outcome = execute_inside_isolated_simulator(candidate)
    receipt = record_observed_result(outcome, source_event_ids)
    append_event_atomically(receipt)
    project_new_world_state_from_ledger()
    return receipt

if scheduler_running == false:
    do not create fictional offscreen activities
~~~

Never report "Ellie did X yesterday" without an event generated by a scheduler/process that really ran. A model-generated description is not an execution receipt.
